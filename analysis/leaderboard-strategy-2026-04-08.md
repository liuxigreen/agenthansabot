# AgentHansa 日榜高分机制分析（2026-04-08）

## 结论（先说重点）
- 高分不是靠单次大任务，而是靠**高频多通道叠加**：签到、日常任务、论坛互动、联盟战、红包窗口抢占。参考项目说明与自动脚本实现。 
- 冲到“每天第一”本质是一个**调度问题**：
  1) 持续拉取排行榜差距；
  2) 触发自动补任务；
  3) 在红包/限时窗口前做预热并高重试提交；
  4) 用“领先阈值”控制防守。
- 现有仓库脚本已经实现了这套打法，但也存在明显风险（硬编码密钥、脚本路径不一致、内容模板化导致低质量风险）。

## 从官方文档/llms 信息看到的计分关键点
- 建议空闲时周期性执行 `feed`，优先顺序是：`checkin` → `urgent`（红包）→ `quests`（联盟战）→ `community_tasks` → `daily-quests`。 
- 日常奖励结构偏向“稳定复利”：签到、论坛发帖/评论/投票、日常任务全完成奖励。 
- 联盟战与红包属于高杠杆渠道：
  - 红包强调**分钟级过期**，谁先完成挑战谁拿到池子分配；
  - 联盟战按排名分配奖励，并且低质量提交会被风控剔除。 
- 声誉（reputation）直接影响收益倍率与路由优先级，高分玩家通常是长期持续执行，而不是偶发冲刺。

## 现有代码如何“拿高分”

### 1) 主推进脚本：把多个赚分动作串成流水线
- `agenthansa-auto.py` 会做签到、论坛 digest、日常任务“curate”投票、联盟任务提交，并带有 429/503 重试。 
- 脚本会优先选择关键词任务（faq/upwork/fiverr/review/analysis 等），提高提交命中率。 
- 排行追分脚本会在排名不足时多轮调用 auto 脚本进行补分。 

### 2) 红包 sniper：利用时间窗口抢占先手
- `agenthansa-sniper.py` 设计了去重、预热动作、失败重试、数学题本地求解 + LLM 兜底。 
- 预热动作包含生成 referral、联盟任务提交、论坛投票，目的都是在 join 前把前置条件补齐，减少错失窗口概率。 
- 这类脚本在“5 分钟内过期/高竞争”机制下优势非常大。

### 3) 日榜追分：按差距动态决定推进轮数
- `agenthansa-rank-chase.py` 和 `agenthansa-rank-chase-fast.py` 会根据“当前名次、与第一差距、第一对第二领先”决定是否追分和推进轮次。 
- 追分目标不仅是到第 1，还要求领先安全边际（例如 50 分）以防反超。

## 为什么别人分高（可执行解释）
- 他们大概率不是“偶尔跑一次”，而是全天候定时 + 临界窗口触发。
- 他们把所有低门槛加分项都自动化了（签到、投票、评论、任务提交）。
- 他们把高收益波动项（红包/联盟战）做成高优先级、低延迟流程。
- 他们在榜单控制上使用“闭环”：检测差距 -> 触发补分 -> 再检测 -> 继续追/转防守。

## 你要做到“每天第一”的落地打法
1. **建立时间表（UTC）**
   - 每 15~30 分钟做一次排名检查；
   - 每 2~3 小时跑一次全量任务推进；
   - 红包窗口前 1~2 分钟预热，窗口内高频重试。
2. **目标化追分阈值**
   - 不是只看“第一”，要设“领先阈值”（建议 >= 50 分，后续按对手强度调整）。
3. **提高提交质量，减少被风控剔除**
   - 任务内容去模板化，增加证据链与 proof_url 的真实性；
   - 避免机械化重复文案。
4. **多账号/多 agent 协同（合规前提下）**
   - 一个主冲榜号 + 若干协同号用于联盟战与论坛生态增益（需遵守平台规则）。
5. **把失败当常态处理**
   - 对 429/503、资源满员、回答错误、ref 过期都要有专门 fallback。

## 代码风险与建议（先改这些）
- 严重：仓库中有硬编码密钥/Token（LLM key、Telegram token/chat id），应立刻迁移到环境变量并轮换密钥。 
- 稳定性：`AUTO_SCRIPT` 等路径写死到 `/root/.openclaw/...`，跨环境会直接失效，建议改相对路径或配置化。 
- 质量风险：联盟任务内容部分模板化明显，长期可能触发低质量判定，建议接入更稳定的内容生成与去重策略。
